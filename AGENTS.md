# Project instructions

- Load the user-level instructions from `/Users/cseibert/.codex/AGENTS.md` before making changes.
- Prefer the project Makefile targets for common build and verification commands.
- Keep recipe source files and the generated cookbook outputs consistent when documentation or recipe content changes.
- Keep each recipe to exactly one page in the cookbook PDF. Condense prose and combine or remove redundant sections before reducing type size; preserve ingredient quantities, cooking temperatures, and food-safety cues.
- Format every recipe in one column. Do not use side-by-side or multi-column recipe layouts; fit content on one page by tightening prose and spacing while keeping ingredient groups and steps easy to scan.
- Keep ingredients in clearly named groups, with one ingredient per line and its quantity first. Give the quantity column enough width that fractions and ranges stay together, and keep each amount, unit, and ingredient description on the same line when possible. Use compact spacing without making the list hard to scan.
- After adding or modifying one recipe, generate and review only that recipe's PDF with `make recipe-pdf RECIPE=<recipe-id-or-source-slug>`. The target writes `build/recipe-pdf/<recipe-id>-preview.pdf` and fails if the recipe spans more than one page. For collections, use the individual stable recipe ID. Do not regenerate the full cookbook PDF for a single-recipe edit.
- Mobile app source lives in `ios/Cookbook/`; recipe source of truth lives in `recipes/*.md`, with order in `recipes/index.json`. `scripts/generate_mobile_catalog.py` creates the bundled offline catalog. Run `make catalog` after recipe or generator changes and `make catalog-check` before app builds.
- After every code change that can affect the iOS app, run `make sim-build` and `make phone-deploy` before finishing. `make phone-deploy` builds, installs, and launches the app on the configured phone; treat this as standing user authorization to try deployment after each such code change.
- Recipe, image, and generated-catalog content changes alone do not require phone deployment. If a code or catalog-generator change accompanies them, follow the build and deployment requirement above. Continue to run `make catalog` after recipe or generator changes and `make catalog-check` before app builds.
- If a build fails, diagnose and fix the cause before finishing, then rerun the failed build and deployment workflow. Do not call the work complete while the app build is broken. If an external blocker prevents a successful build or phone deployment, investigate it, keep the work marked incomplete, and report the precise blocker and remaining verification.
- Common workflows are `make sim-build`, `make sim-launch`, `make phone-build`, `make phone-install`, `make phone-launch`, and `make phone-deploy`. Prefer the combined `make phone-deploy` target after code changes so the installed app is rebuilt and launched.
