## User requirements

- As a cookbook maintainer, I want recipe changes stored in a readable, text-based format in GitHub, so that I can review recipes directly and inspect meaningful line-by-line diffs.
- As a cookbook maintainer, I want a structured database representation for validation and generation, so that HTML, PDF, and mobile outputs come from one consistent recipe snapshot.
- As a reader, I want the PDF generated as a build artifact alongside the HTML output, so that both formats stay available from the same recipe data.
- Keep recipe content human-reviewable in Git. Markdown is the leading candidate for one file per recipe; generate SQLite as a reproducible build/runtime artifact instead of making an opaque binary database the only editable authority.
- Preserve current recipe content, chapter and collection order, stable recipe IDs, the mobile catalog's generated-data contract, and existing GitHub artifact and S3 publication behavior unless implementation identifies a concrete incompatibility.

## Architecture and data model

- Keep a single editable authority in version-controlled Markdown files, one per recipe, so reviewers can read and diff the recipe directly. A five-recipe prototype (Turkey, Ham, Panko Mahi-Mahi, Pork Ramen, Cinnamon Bun) successfully round-tripped the ordered normalized content structure from LaTeX to Markdown and back, and all five regenerated LaTeX files compiled. Treat Markdown as the leading candidate, then harden its grammar and migration converter against the full source corpus before switching authority. Do not maintain independently editable Markdown and SQLite copies.
- Prefer Markdown syntax over cookbook-specific comment markers: ingredient tables identify ingredient groups by their `Quantity | Ingredient` header; `Time | Task` tables represent schedules; labeled blockquotes distinguish introductions, tips, and healthier options; Unicode degree/fraction characters map to the cookbook TeX macros; and a page-break element preserves explicit page breaks. Use ordinary front matter for stable IDs and renderer presets such as `layout: compact`. The prototype used comments and a raw-LaTeX fence as migration scaffolding, but the canonical Markdown should not need them; unknown LaTeX constructs should be reported for review instead of silently copied into recipe prose. This is semantic/content reversibility rather than byte-for-byte source reproduction; whitespace and equivalent macro spellings are normalized.
- Model recipes, ordered chapters/collections, ingredient groups and ordered ingredients, ordered instruction steps and subsection labels, introductions, tips, and healthier options. Keep stable recipe IDs and represent collection entries such as Cocktails as distinct recipes under their collection heading.
- Add schema-version tracking and deterministic validation/import commands. Keep app-specific metadata (stable IDs, ingredient overrides, recipe collections, and step-to-ingredient assignments) in the structured source or a clearly linked text metadata file so it remains visible in review.
- Generate a SQLite database from the validated text sources when a database is useful for app/runtime access. Generate HTML, cookbook LaTeX/PDF input, and the existing iOS JSON catalog from the same validated snapshot. Retain the existing TeX toolchain for pagination if it is the least disruptive PDF renderer; ensure every recipe remains one page and preserve one-column ingredient and instruction layouts.
- Treat generated SQLite, LaTeX/PDF, HTML, and mobile catalog files as build outputs with a documented regeneration path. Avoid hand-editing generated outputs or treating a committed SQLite binary as a second source of truth.
- Update Makefile and GitHub Actions inputs so validation and all renderers consume the same text-source revision. Keep the PDF and HTML as downloadable GitHub Actions artifacts and retain the current `master` S3 publication destinations and conditions.

## Basic test cases

- Preserve the five-recipe prototype artifacts and verify for each that the ordered content tree parsed from original LaTeX equals the tree parsed from Markdown and regenerated LaTeX; compile each regenerated LaTeX file. Refine the prototype to remove cookbook comment markers: infer ingredient groups from quantity/ingredient tables, use labeled blockquotes for introductions/tips/healthier options, distinguish schedules with `Time | Task` tables, and represent page breaks as explicit page-break elements. Confirm human-readable diffs.
- Replace Panko Mahi-Mahi's raw TeX layout fence with front-matter renderer metadata (for example, `layout: compact`) and verify that generated TeX preserves its compact layout. Scan all source macros and fail with a reviewable diagnostic for unsupported constructs rather than embedding them invisibly in prose.
- Parse and validate all current recipes into the text representation; verify recipe IDs/count, chapter order, collection members, ingredient quantities, instructions, tips, and optional metadata against the reviewed source inventory. Report ambiguous or unsupported constructs for manual review rather than silently discarding them.
- Reject an unsupported schema version, malformed source, duplicate IDs, dangling ingredient references, invalid ordering, or a failed SQLite build without producing publishable outputs.
- Add, edit, and remove a recipe in the text source and verify the generated SQLite, HTML, PDF, and mobile catalog reflect that change without manual edits to generated files.
- Include a collection entry and a recipe with multiple ingredient groups, subsections, fractions, temperatures, and special characters; verify they render correctly in HTML and PDF and preserve collection navigation and stable mobile IDs.
- Before switching builds to the new source format, preserve baseline PDF and HTML outputs from the current source revision. Regenerate both from converted data and compare recipe by recipe using stable IDs and HTML anchors/PDF page boundaries. Use normalized HTML text/content comparison as a fast first pass, and report missing, extra, reordered, or substantively changed recipe content. Check ingredient names and quantities, instructions, temperatures, food-safety cues, HTML structure/links, and one-page PDF layout. Treat expected HTML whitespace or PDF typography/spacing changes as review items, and accept substantial deltas only after each is explained and approved.
- Build all outputs from the same source snapshot; verify the HTML and PDF contain the same recipe set and ordering, every recipe occupies exactly one PDF page, the generated SQLite/mobile catalog agree with the text sources, and both web outputs are uploaded as GitHub artifacts. On `master`, verify the existing S3 keys still receive the matching outputs.
- Change no recipe data and rerun generation; verify outputs and catalog are reproducible, the generated database is current, and validation reports no stale generated data.

## High-level implementation details

1. Treat Markdown as the leading candidate based on the five-recipe semantic round-trip and compile trial. Refine the prototype into a documented, versioned, comment-free grammar with unambiguous syntax for ordered ingredient tables, prose/steps, section boundaries, labeled notes, schedules, page breaks, and inline quantities. Use front matter for IDs and renderer presets. Accept the format only after round-trip and render checks cover the full source corpus and collection cases.
2. Inventory the LaTeX grammar, index ordering, collection conventions, and `data/mobile/metadata.json`; design the text schema and converter around actual content and emit a review report for ambiguous constructs. Keep source conversion separate from routine generation so the one-time migration cannot silently rewrite recipes.
3. Convert all current recipes and metadata into the selected text format, compare them with LaTeX and the mobile catalog, resolve discrepancies, and review the resulting diffs. Preserve the existing LaTeX revision as a rollback/baseline until output parity is accepted.
4. Implement deterministic validation and generation of SQLite, HTML, PDF input, and the existing mobile JSON shape. Preserve HTML escaping, recipe ordering, PDF pagination/readability, and mobile stable-ID compatibility. Ensure a fresh checkout can regenerate all derived outputs without a preexisting database.
5. Update Makefile targets, README and architecture docs, and GitHub Actions to validate the text sources before generating outputs and artifacts. Keep S3 upload conditions and keys intact; make a failed validation or render block publication.
6. Pin and retain the pre-migration PDF and HTML before changing the authoritative input. Once conversion and exporters are ready, regenerate both. Compare normalized HTML recipe sections keyed by stable IDs/anchors and compare PDF extracted content/rendered pages by recipe ID and page boundaries. Produce a delta report for reviewers; investigate every substantive change to identity/order, ingredients or amounts, steps, temperatures, safety cues, links, and pagination, and record the disposition of accepted deltas. Then verify a clean build from a fresh checkout, importer/exporter and migration coverage, representative HTML/PDF pages, and CI artifact/S3 configuration. Main risks are lossy LaTeX conversion, unreadable or fragile source syntax, schema drift, nondeterministic generated data, and accidental recipe-ID or mobile-catalog changes.
