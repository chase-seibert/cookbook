## User requirements

- As a home cook, I want a TV-readable menu mode that I can present over AirPlay, so that my household can browse dinner ideas together.
- As a home cook, I want a guided menu discovery flow that starts with protein and then offers matching meal styles and ingredients, so that I can narrow dinner ideas without navigating a numbered wizard.
- As a home cook, I want a live count and an always-visible action to see matching recipes, so that I can browse whenever I have enough ideas.
- As a home cook, I want the wizard to produce a short recipe list from my choices, so that I can start brainstorming without searching the whole cookbook.
- As a home cook, I want to open a suggested recipe and page through one recipe at a time, so that I can explore a focused menu without a dense list.
- As a home cook, I want each recipe to have a large picture, a restaurant-menu-style description, and suggestions for pairings or accompaniments, so that I can picture a complete meal.
- As a home cook, I want a “Let’s eat” action on a recipe, so that I can carry that choice into dinner planning and grocery review.

Discovery interaction: choose at most one label in each group. Protein appears first; once chosen, only meal styles and ingredients with matching recipes are offered. Choosing another label in a group replaces that group’s prior choice while preserving choices in the other groups. A live recipe count and bottom action remain visible throughout; no numbered progress row or Back/Skip/Next controls are shown. AirPlay means presenting the app’s menu view through iOS screen mirroring. Menu descriptions and pairing suggestions are reviewed cookbook copy, not generated at runtime.

## Architecture and data model

- Keep LaTeX recipe files authoritative and the iOS catalog bundled and offline. Add reviewed menu descriptions and pairing data to the existing mobile metadata/catalog generation path, keyed by stable recipe IDs. Pairings should reference stable recipe IDs where they point to another cookbook recipe; accompaniment text can cover items outside the catalog. Do not derive menu copy from titles alone.
- Add a three-group menu-label taxonomy to the reviewed metadata/catalog path: protein, meal style, and specific ingredient. Use normalized ingredient matching plus reviewed aliases or per-recipe overrides to provide friendly labels (for example, “Broccoli” for a matching ingredient) without treating cookbook chapter categories as menu labels. Build shortlist results locally from the bundled catalog; no runtime network or AI is required.
- Extend `Recipe` and the generated `recipes.json` with optional menu description and pairing fields. Bump the catalog schema version if required by the generator’s compatibility policy, and decode the new fields as optional so older bundled catalogs remain readable. This is catalog metadata only; no SwiftData migration is needed unless implementation chooses to persist user-authored menu edits, which is outside the current request.
- Add a progressive discovery view before recipe presentation: show protein choices first, then only matching meal-style and ingredient choices. Allow one selection per group and keep a live matching-recipe count with a pinned bottom action. Omit unavailable choice groups automatically. Opening a result enters the one-recipe menu page; its paging scope follows the selected results. Reuse catalog order and bundled thumbnails, with the current neutral image fallback for missing assets. Keep personal cover photos optional and recipe-ID scoped if they are included.
- Route “Let’s eat” with the selected recipe into the existing dinner scheduling and grocery-review capabilities. Preserve the current explicit date/time choice, duplicate handling, grocery item review, and confirmation before writing to Reminders. Persist dinner selection through `PlannedDinnerRecipe`; do not create a second dinner or grocery store.
- No network, account, or external-display service is required under the screen-mirroring assumption. If native multi-screen AirPlay output is required, confirm it separately because it changes the presentation and device-testing scope.

## Basic test cases

- Open discovery and verify it starts with protein only. Choose a protein and verify only matching meal styles and ingredients appear; unavailable options are omitted.
- Choose one meal style and one ingredient. Verify each group stays single-select, changing a choice replaces only that group, and the live count reflects the intersection in stable cookbook order.
- Verify the pinned bottom action shows the available recipe count and opens results with protein alone or any narrower set of choices. Clear or revise choices and verify results update; no matches provide a useful recovery action.
- Open a recipe from the wizard shortlist and page through the matching results in cookbook order, one recipe at a time.
- Open a recipe from the shortlist and verify its single-recipe menu page appears; return to the shortlist without losing selected labels. Browse all matches and verify a useful no-results state when appropriate.
- Page forward and backward through the selected category, including the first and last recipe; controls do not wrap unexpectedly and the displayed recipe, image, description, and pairing suggestions stay in sync.
- Present the menu over AirPlay/screen mirroring in portrait and landscape layouts. Recipe title, image, description, category, pairing text, and navigation remain legible and operable; a missing image displays the fallback.
- Before implementing the menu UI, review all four task attachments: “Menu Mode - Discovery Wizard Step 1.jpg” for the guided wizard visual language, “Menu Mode - Ingredient Discovery.jpg” for shortlist behavior, and “Menu Mode - Landscape.jpg” and “Menu Mode - Portrait.jpg” for individual recipe presentation.
- Open a recipe with no reviewed menu description or pairings and verify the layout remains complete without blank or misleading copy.
- Tap “Let’s eat,” choose a dinner date/time, and verify the same recipe appears once under that date in Dinner. Add another recipe to the same date and verify both are available to planning.
- Review groceries from the selected recipe, remove an item or keep an already-listed item unselected, and confirm only reviewed items are added to the chosen Reminders list. Canceling either review leaves the dinner/grocery data unchanged as appropriate.
- Regenerate the catalog and run catalog validation; verify optional menu fields decode when present and when absent, stable recipe IDs remain unchanged, and image asset references resolve or fall back safely.

Add focused catalog and UI coverage for label normalization, single selection within each group, cross-group matching, eligible-choice filtering, live result counts, empty groups/results, shortlist order, one-recipe paging, missing metadata/assets, pairing links, handoff state, and grocery confirmation. Risks and unresolved decisions: Confirm the exact label choices and whether the shortlist has a fixed size before offering browse-all. “AirPlay” could require native external-display support instead of ordinary screen mirroring. The breadth of reviewed descriptions and pairings is not specified, so implementation should decide whether to author all recipes or a bounded initial set. Confirm the post-“Let’s eat” destination and whether grocery review is immediate or offered after scheduling.
