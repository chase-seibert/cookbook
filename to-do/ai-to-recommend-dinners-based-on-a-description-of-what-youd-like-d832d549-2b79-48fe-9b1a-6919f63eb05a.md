# Weather-Informed Dinner Suggestions for Cookbook iOS

**Plan status: Approved by the user on 2026-11-13.**

## User requirements

Let someone ask Cookbook for dinner ideas that fit tonight's local weather, using recipes already in their active cookbook. The feature should feel like the weather-to-five-recipes flow: show a short forecast, offer a small set of relevant ideas, and explain why each recipe fits.

- Add an on-demand **Weather picks** entry point in the existing Dinner tab. Do not add background location checks, notifications, or an automatic daily trigger in the first version.
- Let the user choose and save a weather location once (current location or a searched city/ZIP). Reuse it for later Weather picks; provide a clear change/clear action in Settings. If current location is chosen, request foreground location access only when setting it up or refreshing it; do not ask them to choose a place on every feature use.
- If location access is denied, revoked, or unavailable, keep the saved/searchable-place option available. Explain the location use before the system permission prompt.
- Show the dinner-time forecast for the selected local date: concise condition, temperature range, and relevant rain/wind/snow detail. Include WeatherKit attribution and legal link wherever weather information is displayed.
- Recommend up to five active recipes from the full library, including imported recipes. Exclude deleted recipes. Give each card a plain-language reason, such as “comforting for a cool, rainy evening.”
- Let the user open a recipe or add it to tonight in the existing dinner planner. Keep the suggestions useful when weather cannot load by offering a retry and a route back to the normal dinner planner.

## Architecture and data model

The app already has a `DinnerPlannerView` in `ios/Cookbook/SettingsAndDinner.swift`, recipe assembly there (bundled plus active imported recipes, excluding deleted bundled recipes), and recipe metadata in `ios/Cookbook/Catalog.swift`. The app has manual and AI-assisted dinner planning; Weather picks should feed its existing planner rather than create a parallel dinner data model.

Prefer Apple's WeatherKit Swift API behind a small service boundary that returns a typed dinner forecast and attribution data. WeatherKit requires Apple Developer Program membership; it is not automatically available as a free iOS system API to every app. Membership includes up to 500,000 API calls per month, with an optional paid tier above that allowance. Enabling it is documented as a self-service setup: an Account Holder or Admin enables WeatherKit for the App ID in Certificates, Identifiers & Profiles, then adds the capability to the app target and provisions the entitlement. Apple documents no separate WeatherKit capability-approval application; this is an inference from its setup process, and implementation should verify that the team's membership and signing profile can provision the capability. A free Personal Team should not be assumed to qualify for the membership requirement. See [Get Started with WeatherKit](https://developer.apple.com/weatherkit/), [enable app capabilities](https://developer.apple.com/help/account/identifiers/enable-app-capabilities), [WeatherKit attribution](https://developer.apple.com/documentation/weatherkit/weatherattribution), and [WeatherKit entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.weatherkit).

Add a persistent `WeatherLocationPreference` setting with either a named searched place or a user-selected current-location mode. Resolve the place once and reuse it for subsequent forecast requests; do not prompt the user to reselect a location each time. A saved city/ZIP does not require the OS location permission prompt. If the user chooses current location, obtain a foreground fix when setting it up or explicitly refreshing it and use When In Use permission only. If permission is denied/revoked, offer the saved place/search fallback. Avoid Always authorization and background location. Store only the selected place/coordinate needed to reuse the preference, not a location history, and do not persist WeatherKit data beyond its permitted temporary use. Fetch on demand and avoid unnecessary requests.

Make recommendations LLM-powered. Supply the model a compact structured dinner-time forecast and the active cookbook recipes (IDs, titles, ingredient lists, labels, introductions/descriptions, pairings, servings, and source type) and ask it to choose up to five relevant recipes and explain each choice in a short, compelling, grounded reason. Require structured output containing only supplied recipe IDs; validate IDs, uniqueness, result count, and reason length before showing results. Instruct the model to use only supplied recipe facts and forecast signals, avoid inventing ingredients, preparation times, nutrition or dietary claims, and explain the weather connection plainly.

The app already has iOS 26 Foundation Models support for on-device dinner scheduling and a cloud OpenAI Responses API client, Keychain key storage, model setting, and provider picker (`aiProvider`, `openAIModel`, `KeychainKey`, `AIDinnerPlanner`, `OnDeviceDinnerPlanner`). Add a dedicated weather recommendation prompt/schema and provider adapter; reuse the current configuration and credential plumbing rather than adding another key. Support on-device generation where Apple Intelligence is available and wire the existing OpenAI route as a cloud option. Make the provider policy visible: the app's existing AI setting says On-device never falls back to cloud, so preserve that explicit choice unless the user enables a Weather picks-specific cloud fallback. Do not silently send personal recipe text to the cloud. Do not send precise coordinates or the saved location name to the cloud; send only the forecast summary and recipe data needed for ranking.

If the team cannot provision WeatherKit, support a deliberate cloud weather fallback using the OpenAI Responses API `web_search` tool. Passing a city string in a normal model prompt does not fetch live weather; the request must explicitly enable `web_search`, then ask it to find a current dinner-time forecast for the saved city/ZIP and return sourced weather facts for recommendation. The app must show the search sources with the forecast. This route uses the user's configured OpenAI key/model, incurs model token charges plus current web-search tool charges, and sends the chosen city/ZIP and recipe data included in the request to OpenAI. Do not send precise coordinates. Keep this cloud route opt-in and explain its location/data use. See [OpenAI web search](https://developers.openai.com/api/docs/guides/tools-web-search) and [OpenAI API pricing](https://platform.openai.com/pricing/).

For either forecast source, weather facts must be retrieved at request time; do not let the LLM guess from training data or treat stale model knowledge as a current forecast. If WeatherKit is unavailable and the user has not enabled cloud web search, explain the setup choice and keep normal dinner planning available. If neither provider is available or the model response fails validation, show a clear retry/fallback state and optionally use deterministic non-LLM ordering as a degraded path.

## Basic test cases

- The app does not request location before the user enters Weather picks.
- Denying location does not block the feature; manual city/ZIP selection remains available and the place can be changed or cleared.
- A saved searched place is reused across feature launches without another location selection; it can be changed or cleared.
- Current-location selection requests When In Use authorization only as needed; denial/revocation can switch to a saved or searched place.
- On-device model produces up to five unique active recipe IDs with grounded weather explanations; malformed, unknown, duplicate, or unsupported recipe IDs are rejected.
- Cloud fallback uses the existing OpenAI key/model configuration only when the user has permitted cloud processing; the request excludes location name and precise coordinates.
- When WeatherKit is unavailable, the cloud weather option explicitly enables OpenAI `web_search`, searches the saved city/ZIP for a current dinner-time forecast, shows source links, and never treats model memory as live weather. Without explicit cloud-search consent, it asks the user to enable a supported weather source and leaves normal dinner planning available.
- Results include active imported recipes, exclude deleted recipes, and present each model-generated reason alongside its recipe.
- If Foundation Models is unavailable, cloud fallback is disabled, the API key is missing, the network fails, or model output is invalid, show the proper setup/retry/degraded path without preventing normal dinner planning.
- A recipe opens from a result and can be added to tonight through the existing dinner-planning flow.
- Permission denial, no network, unavailable WeatherKit data, and service errors expose a retry or fallback and do not prevent normal dinner planning.
- Forecast date/time uses the selected location's local dinner date/time, and WeatherKit mark/legal attribution is visible wherever weather data appears.

## High-level implementation details

1. Add a persistent preferred weather place and picker UI, with one-time location setup, manual search fallback, change/clear controls, and on-demand forecasts.
2. Verify Apple Developer Program membership and signing-team access, then enable WeatherKit for the App ID and target if available. Display WeatherKit's attribution mark and legal link. If the team cannot provision it, use the opt-in OpenAI web-search forecast path; never embed a private WeatherKit REST signing key in the app.
3. Add a dedicated structured LLM recommendation request. Prefer Foundation Models on supported devices; route to the existing OpenAI Responses API configuration when the user's provider/fallback setting permits. For cloud weather lookup, explicitly enable `web_search`, include only the saved city/ZIP rather than coordinates, and display source links. Keep prompts, decoding, ID validation, and degraded deterministic ranking outside SwiftUI.
4. Add the Weather picks loading, forecast, recommendation, retry, provider status, consent, and unavailable states to the existing Dinner tab.
5. Add focused tests for forecast/location preferences, prompt input construction, structured model output validation, active/imported/deleted recipe handling, cloud privacy boundaries, web-search sources and fallback behavior, and service failure states.
6. Reuse existing recipe navigation and dinner scheduling. After implementation, run `make catalog-check`, then `make sim-build` and `make phone-deploy` as required by the repository workflow. Keep simulator and phone builds sequential, and report any provisioning or device blocker with the verification that remains incomplete.
