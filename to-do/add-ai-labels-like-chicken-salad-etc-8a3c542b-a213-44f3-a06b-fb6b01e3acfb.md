## User requirements

- As a user, I want to browse recipes in the “What’s for dinner?” menu by useful AI-assigned labels such as chicken or salad, so that I can quickly find dinner ideas that fit what I feel like eating.
- As a user, I want labeled results to remain easy to browse, so that selecting a label shows matching recipes without losing the menu’s existing recipe order and presentation.

Assumptions: these are recipe browse labels (which may describe a main ingredient or dish type), not nutrition, allergy, or dietary-suitability claims. AI assists with assigning labels during catalog preparation; labels ship with the offline catalog and are not generated by a live model in the app. The current task context calls this the menu’s “What’s for dinner?” browsing case; exact menu entry-point and label-selection UI should follow that menu’s implementation plan. Confirm if labels instead need runtime generation or user editing.

Illustrative label candidates, grounded in this cookbook and the dinner-browsing use case:

- Main ingredient or protein: `chicken`, `beef`, `pork`, `seafood`, `vegetarian`.
- Dish type: `salad`, `pasta`, `soup & stew`, `casserole`, `pizza & flatbread`, `rice & grain bowl`, `side dish`.
- Dinner occasion or effort: `weeknight-friendly`, `make-ahead`, `holiday / special occasion`, when recipe instructions support the label.

These are starting examples, not a fixed exhaustive taxonomy. A recipe can carry several labels (for example, a chicken recipe can also be a casserole or weeknight-friendly); labels should describe useful browse facets and remain consistent across the catalog.

## Architecture and data model

- Keep the LaTeX cookbook as the recipe-content source and the bundled mobile catalog as the app’s offline read model. Store AI-assisted, reviewed label assignments in `data/mobile/metadata.json`, keyed by each recipe’s stable ID, and have `scripts/generate_mobile_catalog.py` emit them with each recipe. This avoids editing generated `recipes.json` by hand or changing recipe source files just to add browse metadata.
- Add an optional labels field to the decoded `Recipe` catalog model and use it in the “What’s for dinner?” menu’s recipe filtering/presentation. Keep chapter/category filtering intact and combine it predictably with label selection; retain the existing catalog order in results. Normalize label spelling/case and avoid duplicate labels so equivalent labels do not create separate filters.
- No SwiftData persistence or migration is needed for bundled read-only labels. Keep labels optional so catalogs without the field remain decodable; preserve existing recipe IDs and other catalog fields. No runtime AI service, credentials, network request, or account dependency is introduced under the assumption above.

## Basic test cases

- A recipe assigned `chicken` appears when that label is selected; a recipe without that label does not. The same holds for a dish-type label such as `salad`.
- A recipe with multiple labels appears under each applicable label, but appears only once in results when filters overlap or duplicate assignments are present.
- Changing the selected label updates the visible results while preserving cookbook order and the menu’s existing recipe presentation.
- Combine a label with an existing chapter/category selection and verify only recipes satisfying both filters appear; clearing the label restores the category’s full set.
- Select a label with no matching recipes and verify the menu shows a useful empty state and lets the user clear or change the filter.
- Decode a catalog recipe with labels and one without labels; both load successfully. Catalog generation rejects or surfaces assignments for unknown recipe IDs and emits normalized, duplicate-free labels.
- Run `make catalog` and `make catalog-check`; verify stable recipe IDs and current generated catalog output are preserved apart from the new label data.

## High-level implementation details

1. Inspect the menu browsing flow when available and map its category selection, filtering, and ordering to the current browser/catalog behavior. Confirm whether label filters are single-select or multi-select and where they appear in the menu.
2. Define a small, consistent label vocabulary for the initial “What’s for dinner?” use case. Use AI to propose labels for recipes, then review assignments for relevance and consistency; do not infer allergy or dietary guarantees. Keep unreviewed assignments out of the catalog.
3. Extend the metadata-to-catalog generator and `Recipe` decoding model for optional labels. Add validation for referenced stable recipe IDs, normalized label values, and duplicates. Regenerate the bundled catalog with the project’s `make catalog` target and check it with `make catalog-check`.
4. Connect label selection to the menu’s existing recipe filter, preserving category filtering, recipe ordering, empty-state behavior, and existing visual style. Keep this feature read-only and offline.
5. Add focused generator/model and menu-filter coverage for matching, combined filters, overlapping labels, missing labels, empty results, and stable ordering. Verify catalog checks and the relevant simulator browse flow; do not treat a successful build as proof of the menu interaction.

Risks and unresolved decisions: “AI labels” could mean live model generation rather than AI-assisted catalog authoring; that would add latency, privacy, credentials, failure handling, and online/offline behavior and needs a separate design choice. The initial label vocabulary and whether users can select one or several labels also need confirmation during implementation.
