## User requirements

- As a user, I want to browse recipes in the “What’s for dinner?” menu by useful AI-assigned labels such as chicken or salad, so that I can quickly find dinner ideas that fit what I feel like eating.
- As a user, I want labeled results to remain easy to browse, so that selecting a label shows matching recipes without losing the menu’s existing recipe order and presentation.
- As a cookbook owner, I want my existing recipes annotated with all applicable browse labels, so that the label filters work across my cookbook instead of only a hand-picked subset.
- As a home cook, I want browse labels organized into a protein step, an optional meal-style step, and an optional specific-ingredient step, so that the menu can guide me from broad dinner ideas to a useful shortlist.

Assumptions: these are recipe browse labels, not nutrition, allergy, or dietary-suitability claims. AI assists with proposing assignments during catalog preparation; labels are reviewed, shipped with the offline catalog, and are not generated by a live model in the app. Align the groups with Menu Mode task #253’s three-step wizard: Protein (step 1), Meal Style (optional step 2), and Ingredients (optional step 3). Selecting multiple labels within one group matches any selected label; selections across groups refine together. Labels and aliases are curated from this cookbook’s actual recipe content.

Initial label set for the three Menu Mode wizard groups:

- **Protein:** `chicken`, `beef`, `pork`, `fish & seafood`, `turkey`, `eggs`, `beans & lentils`. Show familiar display names and use explicit recipe evidence for every assignment; do not imply a recipe is vegetarian or allergy-safe from this group.
- **Meal Style (optional):** `pasta`, `salad`, `soup & stew`, `casserole`, `pizza & flatbread`, `rice & grains`, `sandwich`, `side dish`.
- **Specific Ingredients (optional):** start with ingredients useful for this cookbook, such as `broccoli`, `carrots`, `tomatoes`, `mushrooms`, `potatoes`, `peppers`, `lentils`, `chickpeas`, `cheese`, and `lemon`. Add values based on actual recipe coverage, with aliases such as `broccoli rabe` mapped deliberately rather than by loose substring matching.

Add a separate non-dinner browse group for the rest of the cookbook, with values such as `breakfast`, `baked goods`, `dessert`, `beverage`, `cocktail`, `snack`, `condiment`, and `preserve`. This keeps the wizard focused on dinner brainstorming while ensuring every catalog recipe still has a useful browse path. The values above are an initial controlled vocabulary; review catalog coverage before implementation and add terms only when supported by recipes. A recipe can carry several labels across groups. Annotate every existing recipe and review assignments against its title, ingredients, and instructions.

## Architecture and data model

- Keep the LaTeX cookbook as the recipe-content source and the bundled mobile catalog as the app’s offline read model. Store the reviewed taxonomy and assignments in `data/mobile/metadata.json`; key recipe assignments by stable recipe ID and have `scripts/generate_mobile_catalog.py` emit them with each recipe. Add assignments for every recipe in the current catalog, including breakfast, baking, beverages, condiments, and preserves, not just dinner mains. This avoids editing generated `recipes.json` by hand or changing recipe source files just to add browse metadata.
- Give each label a stable ID, display name, group ID, order, and normalized aliases. Group metadata records its menu role (`protein`, `meal_style`, `ingredient`, or non-dinner `browse_type`), wizard step when applicable, whether the step is optional, and whether multiple values can be selected. Each recipe stores its assigned label IDs; the generated catalog also exposes group definitions so the UI can render labels in the right phase. The decoded `Recipe` model remains compatible with catalogs that lack these optional fields.
- Use label semantics consistently: selections within one group are ORed, while selections across groups are ANDed. Preserve chapter/category filtering separately and combine it with label results; retain catalog order and avoid duplicate recipe results. Normalize spelling and aliases so equivalent labels do not create separate filters.
- No SwiftData persistence or migration is needed for bundled read-only labels. Keep labels optional so catalogs without the field remain decodable; preserve existing recipe IDs and other catalog fields. No runtime AI service, credentials, network request, or account dependency is introduced under the assumption above.

## Basic test cases

- Verify the Protein, Meal Style, and Ingredients groups expose the planned labels, order, display names, optional-step metadata, and aliases; the non-dinner browse group includes useful labels for breakfast, baking, beverages, condiments, and preserves.
- A recipe assigned `chicken` appears in Protein results; one assigned `salad` appears in Meal Style results; ingredient aliases such as `broccoli rabe` resolve only according to their reviewed mapping.
- Selecting two labels within one group returns recipes matching either; selecting a Protein plus Meal Style or Ingredient label refines results to recipes matching both groups.
- A recipe with multiple labels appears under each applicable label, but only once when assignments overlap or duplicate labels are present.
- Advancing from Protein to optional Meal Style and Ingredients preserves selections, skips optional groups when requested, and produces an ordered shortlist; going back preserves prior choices.
- Changing a selected label updates results while preserving cookbook order and the menu’s recipe presentation.
- Combine a label with an existing chapter/category selection and verify only recipes satisfying both filters appear; clearing the label restores the category’s full set.
- Select a label with no matching recipes and verify the menu shows a useful empty state and lets the user clear or change the filter.
- Verify every recipe in the current catalog receives at least one reviewed, supported label, including non-dinner recipes such as beverages, breakfast, baking, and pantry items. Catalog generation rejects or surfaces missing recipe assignments, unknown label or recipe IDs, invalid group/step references, aliases that collide ambiguously, and duplicate or unnormalized labels.
- Decode catalog recipes with and without label IDs and group definitions; both load successfully, preserving compatibility with older catalogs.
- Run `make catalog` and `make catalog-check`; verify stable recipe IDs and current generated catalog output are preserved apart from the new taxonomy and label data.

5. Add focused generator/model and menu-filter coverage for complete catalog annotation, group metadata, alias matching, phase progression/skip/back behavior, combined filters, overlapping labels, empty results, and stable ordering. Risks and unresolved decisions: “AI labels” could mean live model generation rather than AI-assisted catalog authoring; that would add latency, privacy, credentials, failure handling, and online/offline behavior and needs a separate design choice. Review the initial label vocabulary against full-catalog coverage before authoring assignments; the proposed selection rule is OR within a phase and AND across phases.
