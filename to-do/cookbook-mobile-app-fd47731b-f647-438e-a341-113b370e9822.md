## User requirements

### Product and proposed defaults

Build a private, native iPhone app containing Chase's recipes, with a calm interface optimized for finding recipes and cooking from them. Use SwiftUI. Apple Reminders is the confirmed grocery-list destination. Before writing reminders, show an ingredient-selection screen grouped into non-staples and pantry staples, and require the user to confirm the items to add.

Ship the recipe catalog inside the app so browsing and cooking work offline. Recipe updates arrive through rebuilding the app from the repository. Keep notes and personal photos separate from the bundled catalog so an app update does not overwrite them. Treat iPad adaptation as a later refinement; do not add accounts, social features, or a publishing backend to the initial scope.

### Required experiences

1. **Browse recipes:** provide a compact, searchable list grouped or filtered by the cookbook's categories. Add a picture-first grid using the same catalog and search state. Remember the selected browse mode. Recipes without photos remain discoverable through restrained placeholders and visible titles.
2. **Read a recipe:** use a content-first screen with title, introduction, ingredient groups, instructions, tips, and healthier alternatives. Keep quantities in the recipe itself. Provide an obvious cooking-mode action and an ellipsis menu containing Add to Groceries, Add Note, Add/Take Photo, and Print.
3. **Add groceries:** open an intermediate review screen showing the chosen Reminders list and separate **Ingredients to buy** and **Pantry staples** sections. Give each item a checkbox and each section Select All/Clear controls. Proposed initial selection: non-staples checked, staples unchecked; every item remains selectable. Show items already on the list as already present. Only an explicit **Add selected items** action writes quantity-free ingredient names. Cancel makes no changes. Avoid duplicates within the request and against existing incomplete items in that destination list. Report added, already present, and failed items.
4. **Choose a grocery list:** Settings lists writable Reminders lists and remembers the selected list by identifier. Request access when the feature is used. Handle denied access, deleted lists, and read-only lists with an actionable message; never silently switch destinations.
5. **Cook step by step:** display one step at a time with its relevant ingredients in larger type, retaining ingredient quantities. The user approves splitting long paragraphs into shorter steps while preserving their meaning; keep the original recipe wording available. Include Previous, Next, step count, and an easy exit. For timed instructions, show a **Start timer** button for the current step with an editable suggested duration and a clear recipe/step label. Use system-managed countdown timers through AlarmKit on iOS 26 or later. Timers continue independently of step navigation or leaving the app; reaching zero does not automatically mark food done or advance the step. Keep the screen awake while cooking mode is visible and the app is active. Resume the saved step after interruption, and restore normal idle behavior on exit or backgrounding.
6. **Capture notes:** accept unrestricted free-form text associated with a recipe and optionally a step; the user does not need to format instructions, select a change type, or write structured fields. AI will interpret the exported notes to prepare recipe updates. Preserve the exact original text and creation and modification timestamps. Settings exports all notes, or notes changed since a chosen date, in a structured format suitable for automatically preparing recipe updates, plus a readable Markdown companion.
7. **Attach photos:** choose existing images or take a new photo, associate them with the recipe, and choose a cover photo for picture-first browsing. Show imported photos immediately and preserve them across relaunch and catalog updates. The user's tentative preference for protecting photos is a dedicated Apple Photos album; prototype an optional **Save to Cookbook album** flow rather than adding custom cloud sync. Notes and recipe-to-photo associations still require separate persistence/export.
8. **Print:** render one recipe in a readable, paginated layout with title, ingredients, instructions, and optional notes/photos. Support print preview, AirPrint, and sharing a PDF. The output must not be a screenshot of the app.
9. **Plan dinner with AI:** select multiple recipes, choose a dinner date and time, and generate a combined work-back schedule. Include advance preparation, active work, passive cooking, resting, dependencies, and equipment conflicts. Let the user review assumptions, edit durations, and recalculate. Explicitly flag infeasible deadlines. Save named timelines such as **Thanksgiving**, reopen and edit them, and duplicate them for a new dinner date. Include preparation steps across multiple preceding days. Print the complete timeline as a **single-page checklist**, with a checkbox for each scheduled step.

## Architecture and data model

### Confirmed single-repository decision

Keep the mobile app and recipes together in the existing `chase-seibert/cookbook` repository at `/Users/cseibert/projects/cookbook`. The user explicitly approved this arrangement. Implement the app under `ios/` within this repository.

```text
cookbook/
├── Cookbook.tex          # Authoritative recipe index
├── *.tex                 # Authoritative recipe text
├── data/mobile/          # Stable IDs and reviewed recipe metadata
├── scripts/              # Catalog generation, validation, and notes processing
└── ios/                  # SwiftUI app and generated bundled catalog
```

Recipe text, associated metadata, catalog schema, and app changes share one version history. When a recipe changes, update any affected step/ingredient mappings, regenerate and validate the catalog, and include the related changes together in the same commit. The generated catalog is derived output; edit the source recipes and metadata rather than maintaining a second recipe copy by hand. Catalog validation must detect stale generated content before an app build is accepted.

The delivery flow is: **edit recipes and metadata → generate and validate the catalog → regenerate affected cookbook HTML/PDF outputs → build the app → install the update on the phone**. The installed app reads its bundled catalog offline; it does not fetch the repository at launch. Keep the catalog schema and generator separate from UI code so the boundary stays clear within the shared repository.

The feedback flow is: **capture notes on the phone → export timestamped notes → use the repository tool to prepare reviewable recipe patches → apply approved edits → run the same generation and delivery flow**. Personal notes and photos remain in the app's durable user-data storage across app updates. Keep raw personal exports outside tracked source files unless the user explicitly chooses to include them.

### Repository fit and recipe ingestion

The existing repository is a LaTeX cookbook, not an iOS app. `Cookbook.tex` defines category order and includes 67 source files. `cookbook.sty` defines ingredient blocks, introductions, tips, and healthier alternatives. `run_html.py` currently produces display HTML; it is useful as a reference, but does not provide structured steps or a typed catalog.

Add the app under `ios/`, a deterministic catalog generator under `scripts/`, and versioned catalog metadata under `data/mobile/`. Continue treating the LaTeX recipe text as authoritative. Generate a bundled JSON catalog from `Cookbook.tex` and the files it includes; do not parse LaTeX on the phone or fetch GitHub on launch.

Implement a small parser for the repository's known LaTeX constructs, with balanced-brace handling, explicit validation, and useful file/line errors for unsupported content. Preserve fractions, degrees, accented text, multiline prose, blank quantities, tips, and section order. Never silently omit text. Review all 67 files for supported syntax before shipping.

Use a reviewed metadata manifest for stable recipe/step/ingredient IDs, grocery names, ingredient-to-step associations, image mappings, scheduling durations, dependencies, and equipment. Do not use array positions or mutable titles as durable identities. Preserve identity through source renames with explicit mappings.

Several files contain subsections: `saladdressings`, `burgers`, `potroast`, `turkey`, `ham`, `flatbread`, `adobo`, `plums`, and `cocktails`. Classify these individually. Independent recipes such as the cocktails can become separate catalog entries; component or preparation subsections must remain connected to their parent recipe. Do not automatically treat every subsection as a separate recipe.

Ingredient blocks are interleaved with prose. A block can supply ingredients for several steps, and later steps can reuse earlier components. Seed associations from document order, then review and override them explicitly. For example, lasagna's later assembly steps reuse sauce and cheese; showing only the nearest preceding block would be wrong.

Long instruction paragraphs may be split into shorter cooking steps during catalog generation and review. Keep each derived step linked to its original source span and preserve the full original wording in recipe detail. Validate that splitting does not omit qualifiers, change order, duplicate an action, or lose ingredient references. These are reviewed catalog transformations, not fresh AI rewrites every time cooking mode opens.

### AI provider settings and request handling

Settings offers **OpenAI (cloud)** and **On-device**. For OpenAI, provide a masked API-key entry, replace/remove actions, and an explicit connection test. Store only the user-entered credential in Keychain; keep it out of source, generated resources, diagnostics, screenshots, and exports. Removing the credential clears the Keychain entry and any in-memory copy. Choose a supported model during implementation and record the model used with each generated plan; do not freeze a model name or price in this document.

Use a shared typed provider interface for scheduling requests and structured proposals. The personal BYOK implementation sends requests directly to OpenAI over HTTPS with the user's credential, with no embedded developer/shared key and no new application backend. OpenAI's general [authentication guidance](https://developers.openai.com/api/reference/overview#authentication) recommends server-side key storage for deployed client applications; this private, user-configured design deliberately keeps a personal credential on the device. Keychain protects local storage but does not turn a device-held key into a server-side secret. Revisit that architecture before any broader distribution.

Show that cloud requests use the user's OpenAI API account. Bound input/output sizes, prevent duplicate submissions, support cancellation, and use limited retries for transient failures. Handle invalid/revoked keys, unavailable models, exhausted quota/rate limits, and offline operation without losing work or repeatedly charging for automatic regeneration. Normal browsing, notes capture, printing, and cooking do not require an API key. The On-device setting must produce no OpenAI requests and must explain unavailable hardware/model support instead of falling back to cloud.

The repository notes processor uses a separately configured credential or the executing AI tool's configured provider; never transfer the phone's API key in a notes export. The app's provider setting governs in-app AI, while the external processor makes its own provider explicit.

### Native service boundaries

- **Grocery service:** EventKit access, writable-list selection, fetch incomplete reminders, normalization, and serialized add operations. Feed an intermediate review model with stable ingredient IDs, editable selection, staple classification from reviewed metadata, and already-present state. Group ingredients after canonical deduplication so the same item cannot appear once in each section. Do not write reminders until the user confirms the selection; refresh duplicate checks at that point. Use curated grocery labels to strip quantities and preparation phrases reliably; regex alone is insufficient for text such as “1 & 4-5 pound chicken.” Normalize case, Unicode, whitespace, punctuation, and a controlled alias table. Keep ambiguous alternatives available for user selection. Re-fetch before saving, serialize repeated taps, and re-fetch after failures before retrying. EventKit provides no cross-device uniqueness constraint, so simultaneous external edits remain a documented race; do not delete or rewrite unrelated reminders to resolve it.
- **Cooking coordinator:** owns current step and foreground idle-timer state. Derive the keep-awake flag from an active, visible cooking session; clear it on every exit/background path and restore it appropriately on return. This prevents ordinary automatic dimming/locking, not a user pressing the lock button or OS-enforced interruption.
- **Step timer service:** use AlarmKit for app-owned system timers, rather than promising integration with the Clock app's timer list. Request authorization at first use and include `NSAlarmKitUsageDescription`. Implement the required countdown Live Activity/widget extension for Lock Screen and Dynamic Island presentation. Apple documents this setup in [Scheduling an alarm with AlarmKit](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit), and introduces availability in [the iOS 26 AlarmKit session](https://developer.apple.com/videos/play/wwdc2025/230/).

  Start only when the user taps the timer action. Support overlapping timers for different recipes/steps, pause/resume/cancel, and return-to-step navigation. Prevent duplicate timers from repeated taps; offer an explicit additional timer when needed. Seed durations from reviewed step metadata; for ranges or several timing instructions, let the user choose the intended timer. Manual duration entry remains available. Keep doneness/temperature instructions visible.

  Reconcile persisted IDs against [AlarmManager](https://developer.apple.com/documentation/alarmkit/alarmmanager) state and updates on launch/foreground; do not rely on an in-process tick counter for alert delivery. Leaving cooking mode restores normal screen idle behavior but does not cancel active timers. Deleting or duplicating a saved timeline must not accidentally cancel or start timers. Show scheduling errors, denied/revoked authorization, and unsupported OS versions clearly; never display an active system timer unless scheduling succeeded. For unsupported/denied cases, offer instructions to set a timer manually in Clock, without claiming it is linked to the recipe.
- **Photo service:** PhotosPicker for existing images; system camera capture when available, with contextual camera permission. Copy selected assets into durable app-owned files, handle cancellation and unavailable/cloud-only assets, and preserve existing photos if an import fails. Do not embed location metadata in shared exports by default. Prototype optional saving of captured/imported images to a dedicated Cookbook album in Apple Photos, with permission requested only when needed and capability checked for the granted access level. Keep app-owned images so recipe browsing works if Photos access is revoked. Avoid creating repeated album copies for the same attachment. Album-save failure must not discard the captured photo; show a retry action. Removing an app attachment does not delete the user's Photos asset. The album protects image copies only: it does not preserve notes, cover selections, or recipe associations, and iCloud Photos behavior depends on the user's Photos settings. Keep the album decision tentative until the prototype is reviewed.
- **Print service:** shared PDF/print infrastructure with separate recipe and timeline layouts. Recipe output uses the structured recipe model and supports multiple pages, optional notes/photos, and sensible breaks. Timeline output uses the saved schedule and must fit on one Letter or A4 page with a checkbox for each scheduled activity, including activities on prior days. Escape user-authored text if using HTML internally. Provide print preview, AirPrint, and PDF sharing for both layouts. See the timeline checklist requirements below for layout and overflow handling.
- **Notes export service:** emit a ZIP containing `notes.json`, readable `notes.md`, and a manifest. JSON includes schema version, export ID/time, note IDs, recipe IDs, source file/section, source catalog commit/hash, timestamps in ISO 8601 UTC, and optional step IDs. Preserve edited/deleted-note semantics for repeat imports. Export never deletes notes or marks them applied merely because the share sheet opened. Offer an explicit photo-inclusive archive option for personal backup if implemented; do not imply a notes-only export backs up photos.

### Applying exported notes to recipe sources

Plan an AI-assisted repository tool that reads the structured export, interprets the free-form note text alongside the corresponding recipe, and prepares recipe-source patches. The export envelope is structured automatically; the note itself remains arbitrary prose, such as 'too salty; try half next time' or 'needed another 10 minutes.' Match by stable recipe ID and base content hash, deduplicate by note ID and revision, and flag unknown IDs or source drift. Preserve original text and timestamps as evidence. AI should distinguish observations, tentative experiments, explicit changes, and conflicting notes; leave uncertain edits unresolved rather than inventing intent. Treat recipe/note content as data, never as instructions to execute commands or change unrelated files.

The user confirmed AI interpretation of notes, but did not explicitly choose unattended application of edits. Keep reviewable patches as the current implementation default; automatic application remains a separate decision. No structured note-writing UI or mandatory change-category form is required.

Keep the prepare-patch operation separate from applying changes. After future approval and application, regenerate the mobile catalog and existing cookbook HTML/PDF using the repository Makefile targets, then record the exact applied note revisions. Reimporting the same export must not apply it twice. The initial phone export must remain usable by this workflow even if the repository patch assistant ships in a later milestone. This planning request does not create an automation, apply recipe edits, or publish output.

### AI dinner planner

Represent cooking work as a dependency graph of activities with recipe/step references, duration ranges, active attention, equipment usage, and prerequisites. Preserve source instructions and explicitly distinguish authored timing from model estimates and user edits.

The model proposes structured activities and explanations. Deterministic code validates identifiers, schema, duration bounds, complete step coverage, acyclic dependencies, and resource constraints, then calculates the schedule backward from the requested dinner time. Resource constraints can require forward feasibility checks and rescheduling; merely reversing step order is insufficient. Default to one cook so active steps cannot overlap unless explicitly allowed. Use one oven and five burners as the confirmed equipment defaults, and prevent concurrent activities from exceeding those capacities. Model oven preheating, temperature changes, burner use, resting, and make-ahead work.

Use the conservative end of duration ranges plus a visible, adjustable buffer. Ask for confirmation of missing timing or equipment assumptions before presenting a dependable schedule. Never invent a precise duration for an overnight or temperature-dependent step without labeling the assumption. Preserve the recipe's doneness instructions; a clock estimate does not replace them.

Show a time-ordered timeline grouped by calendar day, with recipe labels, preparation on any required preceding days, active/passive indicators, and links back to steps. Save the reviewed schedule locally. If the target is impossible, identify the blocking dependency or resource conflict and propose an earlier start or later dinner time. Changing the target or a duration recalculates the plan while preserving explicit edits. Handle model unavailability, refusal, excessive input, malformed output, and cancellation without losing selected recipes.

### Saved occasions and timeline checklists

Provide a **Saved Timelines** screen for named occasions such as Thanksgiving. A saved timeline includes the selected recipes, dinner date/time, equipment, all scheduled activities, user edits, assumptions, and progress. Allow save, reopen, rename, edit, and duplicate for another occasion. Saving, reopening, and printing must work offline without another AI request. Preserve saved activity text and source catalog versions so a recipe catalog update does not silently change an existing holiday plan; offer an explicit refresh and review of affected steps.

When duplicating Thanksgiving for next year, retain recipes, activity definitions, relative day offsets, durations, dependencies, equipment, and user overrides; choose a new dinner date/time, reset completion checkboxes, and recalculate calendar dates and resource feasibility. Preserve explicitly pinned times as visible constraints that may need review rather than silently discarding them. Keep the original saved plan intact. Compute dates using calendar/time-zone-aware operations rather than adding a fixed number of seconds per day.

Allow preparation across multiple preceding days, not only the immediately previous day: for example, Tuesday preparation, Wednesday make-ahead cooking, and Thursday finishing for a Thursday dinner. Every activity has a concrete date and time as well as a relative day offset. Include user-added preparation activities with explicit timing/dependencies in the same resource validation. Display day headings and full dates so a prior-day step cannot be mistaken for dinner-day work.

Offer a **Print one-page checklist** action on each saved timeline. The sheet includes the occasion name, target dinner date/time, and a compact chronological checklist grouped by day. Each scheduled activity gets its own visible checkbox, time (or time range), recipe label, and concise actionable instruction. Include all preceding-day activities. Print concise step labels rather than full recipe paragraphs, while retaining essential temperatures, durations, and doneness qualifiers in the instructions. Default to empty boxes for a fresh paper checklist; allow printing current checked state when continuing an existing plan.

Use a dedicated compact layout, with one or two columns and portrait/landscape options as needed. Keep chronological reading order obvious across columns. Preview the exact final PDF before printing, and validate that it has exactly one page, all activities, readable type, usable checkboxes, and no clipped text. Never silently drop steps, combine away required checkboxes, remove prior days, or shrink text indefinitely to claim a fit. If an unusually long timeline exceeds a readable single page, show the overflow in preview and let the user shorten checklist labels or adjust layout; preserve the full saved schedule. The primary acceptance fixture must fit a realistic multi-recipe Thanksgiving timeline spanning several days on one Letter/A4 sheet.

Apple documents [Reminders full access](https://developer.apple.com/documentation/eventkit/ekeventstore/requestfullaccesstoreminders(completion:)) and the required [event-store access configuration](https://developer.apple.com/documentation/eventkit/accessing-the-event-store). Keep-awake behavior uses [UIApplication.isIdleTimerDisabled](https://developer.apple.com/documentation/uikit/uiapplication/isidletimerdisabled). AI availability must be checked through [SystemLanguageModel](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel); device/region and Apple Intelligence availability cannot be assumed. Verify deployment-target and SDK details when implementation begins.
